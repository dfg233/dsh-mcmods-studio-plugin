## 1. 问题 1：`mod_license` 为空导致客户端报错

### 现象

新建 Gradle 工程后，`gradle.properties` 的 `mod_license=` 为空（或 `mods.toml` 的 `license=""`），Forge/NeoForge 启动时因缺失 license 报错。

### 根因

旧代码：

```js
const license = String(input.license ?? meta?.license ?? 'All Rights Reserved').trim()
```

`??` 只对 `null` / `undefined` 生效。新建项目时 `meta.license` 是空字符串 `''`（`lib/meta.js` 的 `str('license')` 默认返回 `''`），于是 `license = ''`，`mod_license=` 写进 `gradle.properties`，`mods.toml` 的 `license="${mod_license}"` 展开为空。

### 现状（工作区已修）

```js
const license = String(input.license ?? meta?.license ?? '').trim() || 'All Rights Reserved'
const gradleLicense = asciiName(license) || 'All Rights Reserved'
```

实测（当前工作区代码，三个加载器，`name=我的模组`、`license` 传空）：

- forge / neoforge：`mod_license=All Rights Reserved`；
- fabric：`"license": "All Rights Reserved"`。

### 修改方向（0.4.1）

1. 提交现有修复（注意与问题 2 一起）；
2. 补自动化用例：`license` 传空串 / 只含中文 → 输出 `All Rights Reserved`；
3. 新建项目表单增加 `license` 字段，默认 `All Rights Reserved`；
4. `mods.toml` 的 `license` 为空时拒绝生成（防御性校验，而不是等客户端报错）；
5. 校验：空 license 生成的工程，`mods.toml` 展开后 `license` 非空。

## 2. 问题 2：`mod_name` 乱码、中文项目名

### 现象

`gradle.properties` 的 `mod_name` 乱码；项目名是中文（默认「我的模组」）。

### 根因

- Gradle 的 `gradle.properties` 按 **ISO-8859-1** 读取，中文写入即乱码；`mods.toml` 的 `displayName` 由 Gradle 的 `processResources` 展开，乱码会传过去。
- 新建项目弹窗默认 `name: '我的模组'`（[client.js](../../client.js) 的 `CreateProjectModal`），用户直接创建就会带中文。

### 现状（工作区已修）

```js
function asciiName(text) {
  return String(text ?? '').replace(/[^\x20-\x7E]/g, ' ').replace(/\s+/g, ' ').trim()
}
const gradleName = asciiName(displayName) || pascal(modid) || modid
```

模板改用 `gradleName` / `gradleLicense` / `gradleDescription` / `gradleAuthors`；实测 `name=我的模组` 时输出 `mod_name=Testmod`（回退到 `pascal(modid)`），无乱码。

### 缺口（不提交、不重装就仍是旧行为）

- UI 默认名仍是中文「我的模组」；
- 中文名会退化成 `Testmod`（modid 派生），用户想要的英文名被丢弃；
- `name` 字段仍保留中文（用于 Java 注释、fabric 的 `name` 已改 `gradleName`），界面上「中文显示名」与「英文 gradleName」没有区分说明。

### 修改方向（0.4.1）

1. 提交现有修复；
2. 新建项目弹窗：
   - 默认名改为英文（如 `My Mod`）；
   - 名称为非 ASCII 时提示「Gradle 工程名需要英文；将使用 `X` 作为英文名」，并显示派生结果；
   - 或直接校验：名称必须为 ASCII（错误提示「项目名请使用英文」）；
3. 内部统一两个字段：`name`（显示名，可中文，写入 `.mcstudio`/Java 注释）与 `gradleName`（英文，写入 Gradle）；
4. 补测试：中文名、纯英文名、带空格名的三种输出；
5. 文档写明「Gradle 工程相关字段必须 ASCII」。

## 3. 问题 3：Gradle 项目现在怎么创建；能否下载官方 MDK

### 现状

插件**不下载 MDK**。创建流程：

1. `project.create`（或 `scaffold.apply`）读取内置模板 `templates/scaffold/<loader>/1.20.1/`；
2. 渲染 `settings.gradle`、`build.gradle`、`gradle.properties`、主类、`mods.toml`（forge/neoforge）或 `fabric.mod.json`、`pack.mcmeta`、`.gitignore`；
3. 复制 `templates/scaffold/shared/` 的 `gradlew`、`gradlew.bat`、`gradle-wrapper.jar`；
4. 已存在文件跳过，失败删除本次新增。

模板来源：forge 的 `settings.gradle` / `build.gradle` / `mods.toml` 取自本地 `testmod-forge-1.20.1`（标准 MDK 结构），由插件脚本复制；neoforge / fabric 为手写。**不联网、不解析 MDK zip**。

### 能否下载官方 MDK

可以，但需要明确成本：

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A 内置模板（现状） | 模板随插件发布 | 离线、快、稳定、可控 | 需随 MC/loader 版本维护；与官方 MDK 最新内容有滞后 |
| B 下载官方 MDK | Forge `net.minecraftforge:forge:<ver>-<mc>:mdk` zip / NeoForge MDK / Fabric example mod zip，解压后替换变量 | 与官方一致、版本可扩展 | 依赖网络/代理；解压安全与清理；MDK 结构与占位符差异大；失败需回退 |
| C 混合 | 默认 A；提供「从官方 MDK 生成」可选动作，失败回退 A | 兼顾 | 维护两条路径，测试成本高 |

### 建议

- **0.4.x**：保持 A，模板来源在文档与 UI 中标注「基于官方 MDK 结构」；
- **0.5.0**：评估 C——新增 `scaffold.preview { source: 'mdk' }`（下载 + 解压 + 变量替换 + 失败回退内置）；
- 若做 B/C，必须：版本矩阵校验（MDK 版本 ↔ MC 版本）、下载超时/代理、zip 路径穿越防护、解压后「已存在文件不覆盖」、失败回滚。

## 4. 问题 4：「生成」按钮与「计划」的定位

### 现状

- 任务卡（计划页）有一排按钮：`上下文`、`生成`、`验证`、`回滚`、`编辑`、`删除`；
- 「生成」→ `task.codegen.preview/apply`，用任务的 `templateRefs` 渲染**固定模板**：只创建文件骨架（如 `ElectronicLock` 的 `TODO`、`ModItems` 的注册行），**不写业务逻辑**；
- `codegen` 同时作为 agent 工具暴露（`mcmods_codegen`），agent 也可以调用它；
- 「计划」页目前是想法/系统/任务的卡片管理，任务有 `goal`、`acceptance`、`verify`、`allowedPaths` 等字段，但页面没有把它们呈现为「计划文档」，也没有驱动 agent 的入口。

### 与你的期望的差距

你期望：**计划 = 规划文档**（帮助 AI 规划进度）；**代码由 agent 生成**，而不是插件按钮固定填充。

这与 [AGENT-PLAN.md](../plans/AGENT-PLAN.md) 早先的结论一致（「C. 混合：保留生成能力，以工具形式暴露，由 agent 调用；生成逻辑唯一实现」）。当前「生成」按钮把「工具能力」直接做成了「界面一键固定生成」，偏离了既定方针。

### 修改方向（0.5.0）

1. **重新定义计划页**
   - 任务 = 一条计划条目：目标、验收标准、允许修改路径、保护路径、上下文需求、状态；
   - 卡片展开显示「计划说明」（goal / acceptance / verify / allowed），可编辑；
   - 状态机：`todo → doing → review → done`，与检查结果联动。
2. **改写「生成」按钮**
   - 首选：改为「准备上下文」或「AI 提示词」——把任务 + 上下文包 + 模板建议整理成一段可复制的提示词，交给 agent；
   - 次选：保留「骨架生成」但改名为「插入骨架（不含业务逻辑）」，并在确认框里明确说明；
   - 不再默认用固定模板生成「看似完整」的类。
3. **主流程改为 agent 驱动**
   - agent 读任务与上下文 → 写完整代码 → `task.apply`（变更集）→ 检查 → 用户验收；
   - `codegen` 保留为 agent 的辅助工具（写标记区块/片段），不让 UI 成为主要入口；
   - UI 提供「变更集预览」（diff、越界、检查结果），而不是「一键填充」。
4. **任务卡按钮收敛**
   - 保留：`上下文`、`验证`、`回滚`；
   - 新增：`复制提示词`（或「交给 AI」）；
   - 移除或降级：`生成`（改为「插入骨架」）。
5. **文档**：PLAN.md / AGENT-PLAN.md 明确「计划=规划文档，代码=agent 产出，插件=约束与验收工具」。

涉及文件：`client.js`（任务卡、计划页、CodegenModal）、`lib/api.js`（新增 `task.prompt` 或在 `context.pack` 里带提示词）、`lib/tools.js`、`docs/PLAN.md`、`docs/plans/AGENT-PLAN.md`。
