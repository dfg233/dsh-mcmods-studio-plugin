# v0.5.3 计划：注册优先导入与形态清理（PATCH）

> 日期：2026-11-17
> 版本：v0.5.3（PATCH）
> 状态：**方案待确认，未实现**
> 关联：[V0.5.2-PLAN.md](V0.5.2-PLAN.md)
> 来源：v0.5.2 验收——`corn_crop_stage0..8` 重新导入后仍显示为独立方块；作者建议以注册项确定物品。

## 0. 摘要

1. **注册优先**：以 Java 注册项（`DeferredRegister` 的 `register("id")`）作为「有哪些物品/方块」的权威来源；资源（模型/贴图）只用于补全，不再凭资源文件名造条目；
2. **资源根补齐**：同时扫描 `src/generated/resources`（datagen 输出）中的 blockstates/models；
3. **旧条目清理**：reimport 时把「不在注册表」的存量条目（如 `corn_crop_stageN`）移入 `removed`，并提供 `import.pruneEntries` 一次性清理。

## 1. 实测根因（v0.5.2 未生效的原因）

以 TutorialMod 为例：

```text
src/generated/resources/assets/tutorial_mod/blockstates/corn_crop.json          ← 权威方块定义
src/generated/resources/assets/tutorial_mod/models/block/corn_crop_stage0..8.json ← 部件模型
src/main/resources/assets/tutorial_mod/textures/block/corn_crop_stage0..8.png   ← 部件贴图
```

- 现有 `collectAssets` 只扫描 `src/main/resources/assets/<modid>`（或 `.mcstudio/assets`），**没有扫描 `src/generated/resources`**；
- 结果：`blockstates` 拿不到 `corn_crop`，但 `blockTextures` 拿到 `corn_crop_stageN` 贴图 → `groupBlockVariants` 的父 id `corn_crop` 不存在 → 不归并，每个 stage 成为独立「方块」；
- 且 reimport（merge）不会删除已存在的旧条目，所以即使归并生效，历史条目仍在。

## 2. 是否可行：注册优先（结论：可行，作为主路径）

Forge 的内容必须注册（`DeferredRegister` + `register("id")`），注册名是唯一权威 id；资源可能缺失、可能由 datagen 生成、可能只存在于 build 产物中。因此：

- **主路径**：解析 Java 注册 → 得到 `{id, kind}` 列表 → 用资源补全贴图/模型；
- **回退路径**：没有可用注册解析结果时，退回现有资源扫描（不破坏旧项目）；
- **边界**：
  - 注册名与资源名可能不一致（如方块 `corn_crop` 的贴图 `corn_crop_stageN`）——资源只用于补全，不产生条目；
  - 动态注册（循环/条件注册）无法静态解析 → 回退扫描；
  - 第三方库注册（其他 mod 的 `DeferredRegister`）需按包/文件归属过滤。

## 3. 目标与非目标

### 目标

- `corn_crop_stage0..8` 这类部件不再成为独立条目；
- 条目的来源可追溯（`source: 'registry' | 'resource'`）；
- 重新导入能清理非注册条目的历史残留；
- 与现有 45 个测试文件兼容。

### 非目标

- 不做完整 Java AST 解析（用正则 + 文件上下文，足够覆盖常见注册写法）；
- 不改 `.mcstudio/items/*.json` 数据格式；
- 不删除用户手动创建的条目（只清理「曾由资源扫描自动创建且当前不在注册表」的条目，需可预览）。

## 4. 设计

### 4.1 注册解析（lib/registry-scan.js）

- 复用 `scanRegistryNames` 的文件遍历与「一个文件一个注册类」上下文；
- 识别：
  - `DeferredRegister<Block>` / `DeferredRegister<Item>` 变量名；
  - `BLOCKS.register("id", ...)` / `ITEMS.register("id", ...)`；
  - `registerBlock("id", ...)` 辅助方法的调用（父方法内 `BLOCKS.register`）；
- 输出 `{ blocks: [id...], items: [id...], creativeTabs: [id...], warnings: [] }`；
- 过滤：跳过 `com.example`/第三方包，只扫描项目自身源码。

### 4.2 导入流程

```text
analyzeImport → collectAssets（main + generated）
  → scanRegistry（主路径）
  → buildEntries:
      registry.blocks → block 条目（资源补全贴图/模型）
      registry.items  → item 条目
      registry 缺失 → 退回资源扫描（标记 source: 'resource'）
  → diff（新增/保留/移除）
  → preview（含 removed 预览）
  → import/reimport（merge 时把 removed 中的「自动生成条目」移除）
```

### 4.3 资源根

- `resolveAssetRoot` 增加 `generated`：`src/generated/resources/assets/<modid>`；
- `collectAssets` 合并两处（main 优先，generated 补齐 blockstates/models）；
- 数据文件（recipes/loot）同样合并 `src/generated/resources/data/<modid>`。

### 4.4 旧条目清理

- `diffEntries` 的 `missing` 区分：
  - `auto`：条目带 `source: 'resource'` 标记（v0.5.2 之前的自动条目无标记 → 按「资源扫描可解释」判定）；
  - `manual`：用户手动创建（`source: 'manual'` 或来自 items.save）→ 不自动删；
- `reimport` 默认把 `auto` 类 missing 移入 `removed`（可 `dryRun` 预览）；
- 新增 `import.pruneEntries { path, dryRun }`：把非注册的自动条目清理掉，返回列表。

## 5. 接口与工具变更

- 新增动作 `import.pruneEntries`（+1 → 132）；
- `analyzeImport` 返回增加 `registry`（解析结果）与 `removed`（可清理条目）；
- `import/reimport` 返回增加 `removed`；
- 条目数据可增 `source` 字段（向后兼容，旧条目无该字段）。

## 6. 测试与验收

- `test/46-registry-import`：
  - 注册 fixture（`ModBlocks`/`ModItems` + 资源）→ 条目只含注册 id；
  - `corn_crop` + `corn_crop_stageN`（blockstate 在 generated、贴图在 main）→ 只保留 `corn_crop`；
  - reimport 后 stage 条目被移除（`removed` 含之）；
  - `import.pruneEntries` dryRun/执行；
- 全量回归（46 文件）。

## 7. 风险

| 风险 | 应对 |
| --- | --- |
| 正则解析漏掉动态注册 | 保留资源扫描回退；输出 warnings |
| 误删用户手动条目 | 只清理 `auto` 类；dryRun 先预览 |
| generated 资源不存在 | 忽略该根，不影响现有行为 |
| 注册名与资源名不一致 | 条目以注册名为准，贴图按模型解析补全 |
