## 0. 摘要

插件是「用户与 agent 之间的翻译与记忆工具」——不是编辑器，也不是代码生成器。

三种角色：

- **用户**：充满想象力的计划师，不一定写代码，但清楚「想要什么、为什么、什么算好」；
- **agent**：顶级程序员，把用户的想法凝成合理的模块、阶段、任务与实现路径；
- **插件**：两者交流的载体——列出项目计划、提供数据与工具、形成跨会话记忆、把代码变成可确认的预览。

工作台围绕四个问题组织：

1. 用户想要什么（**构想**）；
2. agent 打算怎么做（**计划：模块 → 阶段 → 任务**）；
3. 每个任务改了什么、是否可接受（**变更预览与验收**）；
4. 下一个 agent 如何接手（**记忆：计划、上下文、决策**）。

内容线（图形化编辑）与工程线（模板、任务、上下文、检查）继续并行：

- **内容线**：图形化编辑物品、配方、标签、语言、模型等数据；
- **工程线**：构想整理、模块/阶段/任务、模板、上下文包、验收门禁。

事实层由三部分组成：**项目文件与代码结构**、**从 Gradle classpath 提取的 API 索引**、**模板/知识卡**。官方文档是知识卡的来源之一，不是运行时必需。

## 1. 产品定义

### 1.1 用户

- **计划师型用户**：有丰富的模组想法，但不一定写代码，需要 agent 把想法翻译成可执行的结构；
- 会写一点代码、但不想重复搭注册、资源、GUI、网络骨架的开发者；
- 用 AI 推进项目，但被 AI「改错文件、忘记约束、反复搜索」困扰的人。

### 1.2 核心价值

1. **意图可表达**：用户用自然语言说想法，agent 整理成构想卡与未决问题，用户只需确认；
2. **计划可读**：agent 把想法拆成模块 → 阶段 → 任务，用户能看到「先做什么、做到什么程度算完成」；
3. **变更可确认**：每个任务先预览 diff、越界与检查结果，用户确认后才写盘；
4. **记忆可接续**：计划、上下文、决策留在插件里，新的 agent 能快速接手，不必重新理解整个项目；
5. **代码可可视化**：复杂代码以 diff、验收项、检查结果的形式呈现，而不是让用户读源码。

### 1.3 非目标

- 不做完整 IDE：不实现编译、调试、反编译、运行时热重载；
- 不做自由节点式可视化编程：Java 逻辑仍由模板 + agent 任务完成；
- 不试图自动理解任意 Java 架构：模块边界由用户/agent 标注，插件负责索引与验证；
- 不做云端协作、多人实时编辑；
- 不在第一版支持所有 MC 版本与所有加载器。

### 1.4 三者关系

```text
用户（想法） ──说──▶ agent（翻译成模块/阶段/任务/路径） ──写入──▶ 插件（计划、数据、记忆、可视化）
   ▲                                                              │
   └────────────── 确认 / 调整意图 ◀── 预览（diff、验收、检查） ────┘
                                                                │
                                                                ▼
                                                            真实项目
```

插件只做三件事：**保存 intent**（构想与计划）、**提供事实与工具**（结构、API、模板、上下文）、**把结果变成可确认的界面**（diff、验收、回滚）。

### 1.5 操作分配

1. **agent 是插件的主要操作员**：构想、模块、阶段、任务都由 agent 通过工具创建与更新；用户不直接编辑这些数据。
2. **用户只与 agent 交流想法**：用户提出想要什么、确认 agent 的方案；沟通全部发生在 DSH 对话框里，插件不承担聊天。
3. **插件 UI 只保留必要按钮**：以查看为主（计划、构想、变更预览），操作限于「确认 / 回滚 / 预览变更 / 导出计划 / 刷新」等，不做复杂的表单编辑器。
4. **对 agent 开放的接口必须齐全**：每个对象（构想、模块、阶段、任务、计划导出）都要有对应的工具与动作，让 agent 能独立完成「记录想法 → 拆计划 → 实现 → 验收」的全流程。

## 2. 设计原则

1. **事实、意图、任务、验证分层**
   - 事实：代码结构、注册项、资源、构建信息；
   - 意图：用户想要什么、系统边界、不变量；
   - 任务：这次只改什么、允许改哪些文件；
   - 验证：怎么证明改对了。
2. **对话输入，卡片确认**
   - AI 可以把用户的话解析成卡片，但必须让用户确认假设与未决问题。
3. **模板优先，自由发挥其次**
   - 常见模组模式有标准做法；偏离模板要留下决策记录。
4. **图形化改数据，模板/任务改逻辑**
   - 表单不承担 Java 行为编辑，避免变成半成品可视化编程。
5. **给 AI 最小上下文**
   - 一个任务只拿相关系统卡、关键类、模板和约束，不塞整个仓库。
6. **每次变更可预览、可回滚**
   - 先展示将改哪些文件，再写入；写入前自动备份。
7. **默认隐藏代码**
   - 用户想看代码时再展开；工作台首页只显示进度和下一步。
8. **API 签名优先于模型记忆**
   - 从项目依赖提取真实类/方法签名；文档只补“推荐用法”，编译与检查才是事实。

## 3. 用户旅程

### 3.1 简单内容：红宝石剑

```text
用户：我想加一把红宝石剑，攻击力 8，耐久 300，用两个红宝石和一根木棍合成。
  │
  ▼
AI 解析为想法卡：目标、内容、配方、验收
  │  用户确认
  ▼
插件建议模板：tool-set + shaped-recipe + lang + texture
  │
  ▼
工作台生成：物品卡、配方卡、语言条目、贴图占位
  │  用户图形化调整攻击力/耐久/配方
  ▼
“应用到工程”预览：设计数据、资源 JSON、需要生成的 Java
  │  用户确认
  ▼
写入/生成 + 验证：资源引用、配方格式、编译
```

### 3.2 系统内容：Lock 类模组

```text
用户：我想做一个能上锁的门，钥匙可以复制，撬棍能撬开。
  │
  ▼
AI 解析为想法卡 + 系统卡：
  锁状态、钥匙绑定、复制台、交互拦截、网络同步
  │
  ▼
插件建议模板：
  uuid-key-item、lockable-interaction、block-entity-menu、s2c-sync-packet
  │
  ▼
计划页生成任务：
  1. 锁与钥匙的 UUID 绑定
  2. 右键上锁/解锁
  3. 复制台方块实体 + GUI
  4. 撬棍拆卸
  5. 客户端同步
  │
  ▼
每个任务只给相关系统卡、类、模板、验收
  │
  ▼
AI 实现 → 插件检查 → 用户验收
```

### 3.3 每次变更的闭环

```text
想法 → 需求卡 → 系统卡 → 模板 → 任务包 → 上下文包
     → AI 实现 → 差异预览 → 检查 → 用户接受/回滚
```

## 4. 核心对象

> 字段级规格见 [design/IDEA-MODEL.md](design/IDEA-MODEL.md)、[design/SYSTEM-MODEL.md](design/SYSTEM-MODEL.md)、[design/TEMPLATE-SPEC.md](design/TEMPLATE-SPEC.md)、[design/TASK-SPEC.md](design/TASK-SPEC.md)、[design/API-INDEX-SPEC.md](design/API-INDEX-SPEC.md)。

### 4.1 想法卡（Idea）

沿用现有「构想」并扩展，不另起炉灶。它是**用户语言层**：不要求技术细节，允许模糊与不确定，由 agent 负责整理与追问。

| 字段 | 说明 |
| --- | --- |
| `id` / `name` | 标识与名称 |
| `goal` | 用户想实现什么 |
| `loop` | 玩法循环：玩家怎么玩、得到什么反馈 |
| `content` | 涉及物品、方块、配方、声音、GUI 等 |
| `systems` | 涉及系统 id |
| `constraints` | 加载器、MC 版本、依赖、兼容性 |
| `acceptance` | 可验证的验收条件 |
| `assumptions` | AI 的假设，必须显式列出 |
| `openQuestions` | 未决问题，未确认前不应开工 |
| `status` | 构思 / 已确认 / 实现中 / 已验证 / 完成 |

### 4.2 模块卡（Module，原系统卡）

> 界面统一称「模块」；数据文件 `modules.json`（兼容旧 `systems.json`），字段为 `systems` 的超集。

| 字段 | 说明 |
| --- | --- |
| `id` / `name` | 模块标识 |
| `responsibility` | 负责什么 |
| `nonGoals` | 不负责什么 |
| `invariants` | 不能破坏的规则 |
| `entryPoints` | 关键类、方法、注册项 |
| `resources` | 贴图、模型、语言、配方、标签、声音 |
| `dependsOn` | 依赖的其他模块 |
| `checks` | 该模块的验收检查 |
| `status` | 规划中 / 实现中 / 稳定 |

### 4.2.1 阶段（Stage）

模块内的实现阶段（顺序与里程碑），任务挂在阶段下；层级为 **模块 → 阶段 → 任务**。

| 字段 | 说明 |
| --- | --- |
| `id` / `moduleId` | 标识与所属模块 |
| `name` / `goal` | 阶段名与目标 |
| `order` | 顺序 |
| `status` | 规划中 / 进行中 / 完成 |
| `acceptance` | 阶段验收 |

### 4.3 模板（Template）

模板是「带参数的做法包」，不是代码生成器。

| 字段 | 说明 |
| --- | --- |
| `id` / `name` | 模板标识 |
| `loaders` / `mcVersion` | 适用加载器与版本 |
| `category` | item / block / entity / menu / recipe / tag / lang / network / config |
| `parameters` | 参数定义：名称、类型、必填、默认值 |
| `files` | 将生成/修改的文件与模板内容 |
| `registrations` | 需要接入的注册点 |
| `checks` | 生成后必须通过的检查 |
| `instructions` | 给 AI 的填充说明 |

第一批模板：

- `simple-item`
- `tool-set`
- `block-basic`
- `shaped-recipe` / `shapeless-recipe` / `furnace-recipe`
- `item-tag` / `block-tag`
- `lang-pair`
- `model-select`

第二批（Lock 类）：

- `uuid-key-item`
- `lockable-interaction`
- `block-entity-menu`
- `s2c-sync-packet`
- `saved-data-store`
- `config`
- `creative-tab`

### 4.4 任务包（Task）

| 字段 | 说明 |
| --- | --- |
| `id` / `title` | 任务标识 |
| `moduleId` / `stageId` | 所属模块与阶段（`moduleId` 兼容旧 `systemId`） |
| `goal` / `nonGoals` | 这次做什么、不做什么 |
| `templateRefs` | 使用哪些模板 |
| `allowedPaths` | 允许修改的文件/目录（create/modify） |
| `guardPaths` | 只读保护路径 |
| `contextRefs` | 需要喂给 AI 的类、资源、模块卡 |
| `codeRefs` | 项目自身类/符号 |
| `baseStructureHash` | structure-diff 基线 |
| `acceptance` | 可执行的验收条件 |
| `verify` | 验证命令或检查 id |
| `status` | 待做 / 进行中 / 待确认 / 完成 / 阻塞 |
| `confirmed` | 用户是否已确认本任务的变更（默认每次任务确认一次） |
| `result` | 变更摘要、检查结果、回滚点 |

### 4.5 检查与决策

- **Check**：资源存在、注册配对、允许路径、编译、NBT 往返、模板一致性等；
- **Decision**：为什么偏离模板、为什么换方案、影响哪些系统；不写决策就默认按模板。

### 4.6 API 索引（支撑层）

不是用户对象，但决定 AI 是否在猜 API。

| 字段 | 说明 |
| --- | --- |
| `loader` / `mcVersion` | 从构建文件识别 |
| `classpathHash` | 依赖与构建文件摘要，用于失效 |
| `classes` | 类名、kind、修饰符、方法/字段签名 |
| `packages` | 分片，按需加载 |
| `stats` | jar 数、类数、包数 |
| `source` | 静态缓存扫描 / Gradle classpath 导出 |

规则：

- 签名以真实 classpath 为准，不以模型记忆为准；
- 默认不执行构建脚本；精确模式由用户开启；
- 查询只回签名摘要，任务上下文最多 20 个类 / 4KB；
- 找不到就返回 `unknown`，不猜；
- 完整规格见 [design/API-INDEX-SPEC.md](design/API-INDEX-SPEC.md)。

## 5. 数据与文件

```text
<项目>/.mcstudio/
├── project.json          # 项目元数据（已有）
├── features.json         # 想法卡（沿用并扩展字段）
├── systems.json          # 系统卡（新增）
├── tasks.json            # 任务包（新增）
├── decisions.json        # 决策记录（新增）
├── items/<id>.json       # 物品设计数据（已有）
├── summary.json          # 派生摘要（已有，扩展计数）
├── structure.json        # 代码结构事实（已有，扩展系统注解）
├── studio.json           # 工坊标记（已有）
└── backups/              # 由插件数据目录统一管理（已有）
```

API 索引不写进项目：

```text
$DSH_HOME/mcmods-studio/cache/api/
  <projectHash>-<classpathHash>/
    meta.json
    classes/<package>.json
```

它是派生缓存，可安全删除；构建文件或依赖变化时重建。

资源文件仍写入工程标准路径：

```text
src/main/resources/assets/<modid>/...
src/main/resources/data/<modid>/...
src/main/java/...
```

兼容规则：

- 新文件缺失时按空处理，不阻塞旧项目；
- `features.json` 只增可选字段，旧记录可读；
- 现有 194 项测试必须保持通过；
- 数据格式变更按 `VERSION-PLAN` 迁移，不静默破坏。

### 6.1 Host 模块

### 6.3 Agent 工具（示意）

```text
mcmods_idea      查看/保存构想
mcmods_plan      模块 / 阶段 / 任务计划
mcmods_module    保存模块（职责、不变量、依赖）
mcmods_stage     保存阶段（模块内顺序）
mcmods_task      创建/读取/更新/确认任务
mcmods_template  查询/渲染模板
mcmods_api       查询 API 索引（签名/类/包）

mcmods_check     运行或读取检查结果
```

工具输出保持紧凑：列表只回 id/名称/状态；全文按需读取。

### 6.4 Client 页面

```text
[想法] [计划] [内容] [验证] [代码]        ⚙
```

- **构想**：只读列表（agent 创建/更新），显示想法、状态、关联任务数；
- **计划**：模块 → 阶段 → 任务（只读），任务级「预览变更 / 确认 / 回滚」；
- **内容**：物品、配方、标签、语言、模型；
- **验证**：检查项、最近构建、任务验收；
- **代码**：可选，按需展开；
- **设置**：齿轮入口保留，后置。

### 6.5 与现有模块的关系

- 现有「构想」→ 想法卡；
- 现有「物品/素材」→ 内容视图；
- 现有 `structure.json` → 事实层；
- 现有 `summary.json` → 派生摘要，新增 `ideas/systems/tasks` 计数；
- 现有 `lib/backup.js` → `change.apply` 的备份与回滚基础；
- 现有工具与测试 → 继续复用，不另起一套。

## 7. 图形化数据编辑

### 7.1 三层数据

| 层 | 例子 | 是否图形化 | 生效方式 |
| --- | --- | --- | --- |
| 资源 JSON | 配方、标签、语言、模型、blockstate | 是 | 直接写文件 |
| 设计数据 | 物品属性、方块属性、创造标签成员 | 是 | 生成代码或任务 |
| 代码逻辑 | 事件、网络、GUI、状态机 | 否 | 模板 + 任务 |

### 7.2 MVP 范围

- 物品 6 个高频属性：堆叠、耐久、攻击、食物恢复、稀有度、附魔光效；
- 配方：有序 / 无序 / 熔炉；
- 标签：物品标签、方块标签；
- 语言：`zh_cn` / `en_us` 同步编辑；
- 模型：`generated` / `handheld` / 自定义；
- 应用预览：区分设计数据、资源文件、需要生成/交给任务的代码。

### 7.3 交互

```text
物品列表 → 点击物品 → 右侧属性面板
  [属性] [配方] [标签] [语言] [模型]
  → 修改 → 校验 → “应用到工程”
  → 预览：将改哪些文件
  → 确认 → 备份 → 写入/生成 → 刷新
```

- 列表内联编辑常用字段，减少弹窗；
- 非法值即时提示，不等到保存；
- AI 可以提议变更，但以表单 diff 展示，由用户确认；
- 每次应用前自动备份，支持撤销。

### 7.4 应用管线

```text
用户修改
  → 校验（id、数值、资源引用）
  → 生成变更集
  → 分类：设计数据 / 资源文件 / 代码或任务
  → 预览 diff
  → 备份
  → 应用
  → 重新生成 summary/structure
  → 返回结果与回滚点
```

不在用户不知情的情况下直接改 Java；代码类变更进入任务包或代码生成预览。

## 8. AI 协作

### 8.1 想法解析

AI 负责把自然语言解析为想法卡，但必须：

- 列出假设；
- 列出未决问题；
- 给出验收条件；
- 等待用户确认后再生成任务。

插件不调用模型；插件提供工具、schema 和存储，解析由 DSH 会话中的 AI 完成。

### 8.2 模板

- 模板清单内置在插件 `templates/` 目录，按加载器/版本分组；
- 模板只提供骨架、注册、资源和检查，不试图覆盖所有业务逻辑；
- AI 可以选模板、填参数、申请偏离；偏离必须写决策。

### 8.3 上下文包

一个任务的上下文包最多包含：

- 1 张系统卡；
- 1–2 个模板；
- 相关类/资源清单（不超过 10 个文件）；
- 任务需要的 API 签名（最多 20 个类 / 4KB）；
- 不变量、允许路径、验收条件。

目标是让 AI 不需要全仓库 grep，也不需要读无关文件，更不需要凭记忆编 API。

### 8.4 任务包

任务包是 AI 的工作单，也是插件的验收依据。没有任务包，不允许 AI 直接改工程。

### 8.5 验收门禁

按优先级实现：

1. 允许路径检查：只改了任务允许的文件；
2. guard 路径检查：只读保护文件未被改动；
3. 结构 diff：相对基线只出现预期变化；
4. 资源引用检查：模型、贴图、语言、声音、标签存在；
5. 注册配对检查：方块 + 方块实体 + 物品、菜单 + 屏幕、包 + 注册；
6. 编译检查：`gradlew compileJava`（用户可选、带超时）；
7. 行为检查：由任务自定义（NBT 往返、配方可合成等）。

检查结果写入任务，不通过不标记完成。

### 8.6 构想与 agent 的交接

- 用户只在 DSH 对话中描述想法；agent **自行**创建/更新构想卡，不需要用户在插件里点按钮；
- 用户要求「整理成计划」时，agent 把构想拆成模块 / 阶段 / 任务，写入计划页；
- 用户通过插件只读查看计划，并在任务级确认/回滚；构想状态随任务完成回填（想法 → 已规划 → 已实现）。

### 8.7 跨会话记忆

- 计划（模块/阶段/任务）、决策、上下文包、项目接手指南（handoff）共同构成记忆；
- 新 agent 先读 handoff + 计划摘要，再按需读取任务详情与上下文；
- 记忆随项目保存，不依赖会话生命周期。

## 11. 风险与应对

| 风险 | 应对 |
| --- | --- |
| 对象模型过度设计 | 先做 4 个对象，字段够用即可；用 Lock 样张验证 |
| 模板爆炸 | 只做高频模式；模板可组合，不为每个功能建模板 |
| AI 解析出错误假设 | 假设/未决问题必须显式确认，未确认不开工 |
| 代码生成破坏手写代码 | 只改标记区块；生成前 diff；失败回滚 |
| API 索引解析不准/缓存布局变化 | 优先使用 Gradle classpath 导出；静态扫描只作回退；索引标记 `source` 与 `classpathHash` |
| 精确索引执行构建脚本 | 默认不执行；用户显式开启 `--offline`、超时、只读 init 脚本 |
| 无 JDK/无 Gradle 环境 | 返回 `unavailable`，任务上下文标记 `apiUnknown`，不阻塞内容编辑 |
| 检查器执行编译有安全/性能风险 | 用户显式开启、超时、只读检查优先 |
| UI 又变成文件树 | 默认系统卡/任务卡，代码折叠 |
| 现有功能回归 | 每次改动跑全量测试；旧字段只增不改 |
| 范围失控 | 每个里程碑只承诺验收标准内的能力 |

## 13. 执行前确认

以下为当前已确认的方向（2026-11-08）：

1. **产品定位**：用户是计划师、agent 是程序员、插件是翻译与记忆工具；
2. **操作分配**：agent 是主要操作员，用户只对话；插件 UI 只保留必要按钮，agent 接口齐全；
3. **对象层级**：模块（界面称模块）→ 阶段 → 任务；
4. **确认粒度**：默认每次任务确认一次（任务级预览 + 确认）；
5. **构想与计划**：构想 = 意图入口，计划 = agent 的承诺与路径，两页保留；
6. **代码生成**：不再以固定模板一键生成为主路径，代码由 agent 产出、任务级预览确认。

下一步从 M0 开始：先写 schema 和样张，不写代码。
