> 关联：[VERSION-PLAN.md](VERSION-PLAN.md)、[STATUS.md](STATUS.md)、[REFERENCE-CUIGENGJI.md](REFERENCE-CUIGENGJI.md)、[旧路线存档](archive/PLAN-v0.1.md)

## 0. 摘要

插件从「模组内容管理器」升级为「**AI 模组工程工作台**」：

> 用户用自然语言描述想象中的模组，插件把想法变成结构化的需求卡、系统卡和任务包；AI 拿到刚好够用的上下文和模板去实现；插件负责预览、约束和验收。

两条主线并行：

- **内容线**：图形化编辑物品、配方、标签、语言、模型等数据，让用户直接看到并修改自己的模组；
- **工程线**：想法解析、系统卡、模板、任务包、上下文包、验收门禁，让 AI 少检索、少猜、少越界。

事实层由三部分组成：**项目文件与代码结构**、**从 Gradle classpath 提取的 API 索引**、**模板/知识卡**。官方文档是知识卡的来源之一，不是运行时必需。

工作台默认显示「现在做什么、下一步是什么」，代码是可选视图，不是首页。

## 1. 产品定义

### 1.1 用户

- 想做一个模组，但不熟悉 Java / Forge / NeoForge / Fabric 的玩家；
- 会写一点代码，但不想重复搭注册、资源、GUI、网络骨架的开发者；
- 用 AI 推进项目，但被 AI「改错文件、忘记约束、反复搜索」困扰的人。

### 1.2 核心价值

1. **想法可落地**：一句自然语言能变成需求卡、系统卡和任务；
2. **数据可直改**：物品属性、配方、标签、语言、模型有图形界面；
3. **AI 有边界**：模板和任务包限定它能改什么、必须满足什么；
4. **结果可验收**：每次变更都有预览、检查、备份和回滚；
5. **工作台可读**：默认不展示 31 个类和 168 个方法，只展示系统和下一步。

### 1.3 非目标

- 不做完整 IDE：不实现编译、调试、反编译、运行时热重载；
- 不做自由节点式可视化编程：Java 逻辑仍由模板 + AI 任务完成；
- 不试图自动理解任意 Java 架构：系统边界由用户/AI 标注，插件负责索引与验证；
- 不做云端协作、多人实时编辑；
- 不在第一版支持所有 MC 版本与所有加载器。

## 2. 设计原则

1. **事实、意图、任务、验证分层**
   - 事实：代码结构、注册项、资源、构建信息；
   - 意图：用户想要什么、系统边界、不变量；
   - 任务：这次只改什么、允许改哪些文件；
   - 验证：怎么证明改对了。
2. **对话输入，卡片确认**
   - AI 可以把用户的话解析成卡片，但必须让用户确认假设与未决问题。
3. **模板优先，自由发挥其次**
   - 常见模组模式有标准做法；偏离模板要留下决策记录。
4. **图形化改数据，模板/任务改逻辑**
   - 表单不承担 Java 行为编辑，避免变成半成品可视化编程。
5. **给 AI 最小上下文**
   - 一个任务只拿相关系统卡、关键类、模板和约束，不塞整个仓库。
6. **每次变更可预览、可回滚**
   - 先展示将改哪些文件，再写入；写入前自动备份。
7. **默认隐藏代码**
   - 用户想看代码时再展开；工作台首页只显示进度和下一步。
8. **API 签名优先于模型记忆**
   - 从项目依赖提取真实类/方法签名；文档只补“推荐用法”，编译与检查才是事实。

## 3. 用户旅程

### 3.1 简单内容：红宝石剑

```text
用户：我想加一把红宝石剑，攻击力 8，耐久 300，用两个红宝石和一根木棍合成。
  │
  ▼
AI 解析为想法卡：目标、内容、配方、验收
  │  用户确认
  ▼
插件建议模板：tool-set + shaped-recipe + lang + texture
  │
  ▼
工作台生成：物品卡、配方卡、语言条目、贴图占位
  │  用户图形化调整攻击力/耐久/配方
  ▼
“应用到工程”预览：设计数据、资源 JSON、需要生成的 Java
  │  用户确认
  ▼
写入/生成 + 验证：资源引用、配方格式、编译
```

### 3.2 系统内容：Lock 类模组

```text
用户：我想做一个能上锁的门，钥匙可以复制，撬棍能撬开。
  │
  ▼
AI 解析为想法卡 + 系统卡：
  锁状态、钥匙绑定、复制台、交互拦截、网络同步
  │
  ▼
插件建议模板：
  uuid-key-item、lockable-interaction、block-entity-menu、s2c-sync-packet
  │
  ▼
计划页生成任务：
  1. 锁与钥匙的 UUID 绑定
  2. 右键上锁/解锁
  3. 复制台方块实体 + GUI
  4. 撬棍拆卸
  5. 客户端同步
  │
  ▼
每个任务只给相关系统卡、类、模板、验收
  │
  ▼
AI 实现 → 插件检查 → 用户验收
```

### 3.3 每次变更的闭环

```text
想法 → 需求卡 → 系统卡 → 模板 → 任务包 → 上下文包
     → AI 实现 → 差异预览 → 检查 → 用户接受/回滚
```

## 4. 核心对象

> 字段级规格见 [design/IDEA-MODEL.md](design/IDEA-MODEL.md)、[design/SYSTEM-MODEL.md](design/SYSTEM-MODEL.md)、[design/TEMPLATE-SPEC.md](design/TEMPLATE-SPEC.md)、[design/TASK-SPEC.md](design/TASK-SPEC.md)、[design/API-INDEX-SPEC.md](design/API-INDEX-SPEC.md)。

### 4.1 想法卡（Idea）

沿用现有「构想」并扩展，不另起炉灶。

| 字段 | 说明 |
| --- | --- |
| `id` / `name` | 标识与名称 |
| `goal` | 用户想实现什么 |
| `loop` | 玩法循环：玩家怎么玩、得到什么反馈 |
| `content` | 涉及物品、方块、配方、声音、GUI 等 |
| `systems` | 涉及系统 id |
| `constraints` | 加载器、MC 版本、依赖、兼容性 |
| `acceptance` | 可验证的验收条件 |
| `assumptions` | AI 的假设，必须显式列出 |
| `openQuestions` | 未决问题，未确认前不应开工 |
| `status` | 构思 / 已确认 / 实现中 / 已验证 / 完成 |

### 4.2 系统卡（System）

| 字段 | 说明 |
| --- | --- |
| `id` / `name` | 系统标识 |
| `responsibility` | 负责什么 |
| `nonGoals` | 不负责什么 |
| `invariants` | 不能破坏的规则 |
| `entryPoints` | 关键类、方法、注册项 |
| `resources` | 贴图、模型、语言、配方、标签、声音 |
| `dependsOn` | 依赖的其他系统 |
| `checks` | 该系统的验收检查 |
| `status` | 规划中 / 实现中 / 稳定 |

### 4.3 模板（Template）

模板是「带参数的做法包」，不是代码生成器。

| 字段 | 说明 |
| --- | --- |
| `id` / `name` | 模板标识 |
| `loaders` / `mcVersion` | 适用加载器与版本 |
| `category` | item / block / entity / menu / recipe / tag / lang / network / config |
| `parameters` | 参数定义：名称、类型、必填、默认值 |
| `files` | 将生成/修改的文件与模板内容 |
| `registrations` | 需要接入的注册点 |
| `checks` | 生成后必须通过的检查 |
| `instructions` | 给 AI 的填充说明 |

第一批模板：

- `simple-item`
- `tool-set`
- `block-basic`
- `shaped-recipe` / `shapeless-recipe` / `furnace-recipe`
- `item-tag` / `block-tag`
- `lang-pair`
- `model-select`

第二批（Lock 类）：

- `uuid-key-item`
- `lockable-interaction`
- `block-entity-menu`
- `s2c-sync-packet`
- `saved-data-store`
- `config`
- `creative-tab`

### 4.4 任务包（Task）

| 字段 | 说明 |
| --- | --- |
| `id` / `title` | 任务标识 |
| `systemId` | 所属系统 |
| `goal` / `nonGoals` | 这次做什么、不做什么 |
| `templateRefs` | 使用哪些模板 |
| `allowedPaths` | 允许修改的文件/目录（create/modify） |
| `guardPaths` | 只读保护路径 |
| `contextRefs` | 需要喂给 AI 的类、资源、系统卡 |
| `codeRefs` | 项目自身类/符号 |
| `baseStructureHash` | structure-diff 基线 |
| `acceptance` | 可执行的验收条件 |
| `verify` | 验证命令或检查 id |
| `status` | 待做 / 进行中 / 待验证 / 完成 / 阻塞 |
| `result` | 变更摘要、检查结果、回滚点 |

### 4.5 检查与决策

- **Check**：资源存在、注册配对、允许路径、编译、NBT 往返、模板一致性等；
- **Decision**：为什么偏离模板、为什么换方案、影响哪些系统；不写决策就默认按模板。

### 4.6 API 索引（支撑层）

不是用户对象，但决定 AI 是否在猜 API。

| 字段 | 说明 |
| --- | --- |
| `loader` / `mcVersion` | 从构建文件识别 |
| `classpathHash` | 依赖与构建文件摘要，用于失效 |
| `classes` | 类名、kind、修饰符、方法/字段签名 |
| `packages` | 分片，按需加载 |
| `stats` | jar 数、类数、包数 |
| `source` | 静态缓存扫描 / Gradle classpath 导出 |

规则：

- 签名以真实 classpath 为准，不以模型记忆为准；
- 默认不执行构建脚本；精确模式由用户开启；
- 查询只回签名摘要，任务上下文最多 20 个类 / 4KB；
- 找不到就返回 `unknown`，不猜；
- 完整规格见 [design/API-INDEX-SPEC.md](design/API-INDEX-SPEC.md)。

## 5. 数据与文件

```text
<项目>/.mcstudio/
├── project.json          # 项目元数据（已有）
├── features.json         # 想法卡（沿用并扩展字段）
├── systems.json          # 系统卡（新增）
├── tasks.json            # 任务包（新增）
├── decisions.json        # 决策记录（新增）
├── items/<id>.json       # 物品设计数据（已有）
├── summary.json          # 派生摘要（已有，扩展计数）
├── structure.json        # 代码结构事实（已有，扩展系统注解）
├── studio.json           # 工坊标记（已有）
└── backups/              # 由插件数据目录统一管理（已有）
```

API 索引不写进项目：

```text
$DSH_HOME/mcmods-studio/cache/api/
  <projectHash>-<classpathHash>/
    meta.json
    classes/<package>.json
```

它是派生缓存，可安全删除；构建文件或依赖变化时重建。

资源文件仍写入工程标准路径：

```text
src/main/resources/assets/<modid>/...
src/main/resources/data/<modid>/...
src/main/java/...
```

兼容规则：

- 新文件缺失时按空处理，不阻塞旧项目；
- `features.json` 只增可选字段，旧记录可读；
- 现有 194 项测试必须保持通过；
- 数据格式变更按 `VERSION-PLAN` 迁移，不静默破坏。

## 7. 图形化数据编辑

### 7.1 三层数据

| 层 | 例子 | 是否图形化 | 生效方式 |
| --- | --- | --- | --- |
| 资源 JSON | 配方、标签、语言、模型、blockstate | 是 | 直接写文件 |
| 设计数据 | 物品属性、方块属性、创造标签成员 | 是 | 生成代码或任务 |
| 代码逻辑 | 事件、网络、GUI、状态机 | 否 | 模板 + 任务 |

### 7.2 MVP 范围

- 物品 6 个高频属性：堆叠、耐久、攻击、食物恢复、稀有度、附魔光效；
- 配方：有序 / 无序 / 熔炉；
- 标签：物品标签、方块标签；
- 语言：`zh_cn` / `en_us` 同步编辑；
- 模型：`generated` / `handheld` / 自定义；
- 应用预览：区分设计数据、资源文件、需要生成/交给任务的代码。

### 7.3 交互

```text
物品列表 → 点击物品 → 右侧属性面板
  [属性] [配方] [标签] [语言] [模型]
  → 修改 → 校验 → “应用到工程”
  → 预览：将改哪些文件
  → 确认 → 备份 → 写入/生成 → 刷新
```

- 列表内联编辑常用字段，减少弹窗；
- 非法值即时提示，不等到保存；
- AI 可以提议变更，但以表单 diff 展示，由用户确认；
- 每次应用前自动备份，支持撤销。

### 7.4 应用管线

```text
用户修改
  → 校验（id、数值、资源引用）
  → 生成变更集
  → 分类：设计数据 / 资源文件 / 代码或任务
  → 预览 diff
  → 备份
  → 应用
  → 重新生成 summary/structure
  → 返回结果与回滚点
```

不在用户不知情的情况下直接改 Java；代码类变更进入任务包或代码生成预览。

## 8. AI 协作

### 8.1 想法解析

AI 负责把自然语言解析为想法卡，但必须：

- 列出假设；
- 列出未决问题；
- 给出验收条件；
- 等待用户确认后再生成任务。

插件不调用模型；插件提供工具、schema 和存储，解析由 DSH 会话中的 AI 完成。

### 8.2 模板

- 模板清单内置在插件 `templates/` 目录，按加载器/版本分组；
- 模板只提供骨架、注册、资源和检查，不试图覆盖所有业务逻辑；
- AI 可以选模板、填参数、申请偏离；偏离必须写决策。

### 8.3 上下文包

一个任务的上下文包最多包含：

- 1 张系统卡；
- 1–2 个模板；
- 相关类/资源清单（不超过 10 个文件）；
- 任务需要的 API 签名（最多 20 个类 / 4KB）；
- 不变量、允许路径、验收条件。

目标是让 AI 不需要全仓库 grep，也不需要读无关文件，更不需要凭记忆编 API。

### 8.4 任务包

任务包是 AI 的工作单，也是插件的验收依据。没有任务包，不允许 AI 直接改工程。

### 8.5 验收门禁

按优先级实现：

1. 允许路径检查：只改了任务允许的文件；
2. guard 路径检查：只读保护文件未被改动；
3. 结构 diff：相对基线只出现预期变化；
4. 资源引用检查：模型、贴图、语言、声音、标签存在；
5. 注册配对检查：方块 + 方块实体 + 物品、菜单 + 屏幕、包 + 注册；
6. 编译检查：`gradlew compileJava`（用户可选、带超时）；
7. 行为检查：由任务自定义（NBT 往返、配方可合成等）。

检查结果写入任务，不通过不标记完成。

## 9. 里程碑

> 版本号是建议，最终以确认后的 [VERSION-PLAN](VERSION-PLAN.md) 为准：v0.x 为测试原型；
> v1.0.0 为正式稳定版；之后的阶段目标属于 MINOR，里程碑内的小功能与修复属于 PATCH，
> 只有底层架构变化才升 MAJOR。

### M0 · 规格与样张（2–3 天）

- 定稿 Idea / System / Template / Task schema；
- 写 1 个简单物品、1 个 Lock 类系统的系统卡样张；

## 11. 风险与应对

| 风险 | 应对 |
| --- | --- |
| 对象模型过度设计 | 先做 4 个对象，字段够用即可；用 Lock 样张验证 |
| 模板爆炸 | 只做高频模式；模板可组合，不为每个功能建模板 |
| AI 解析出错误假设 | 假设/未决问题必须显式确认，未确认不开工 |
| 代码生成破坏手写代码 | 只改标记区块；生成前 diff；失败回滚 |
| API 索引解析不准/缓存布局变化 | 优先使用 Gradle classpath 导出；静态扫描只作回退；索引标记 `source` 与 `classpathHash` |
| 精确索引执行构建脚本 | 默认不执行；用户显式开启 `--offline`、超时、只读 init 脚本 |
| 无 JDK/无 Gradle 环境 | 返回 `unavailable`，任务上下文标记 `apiUnknown`，不阻塞内容编辑 |
| 检查器执行编译有安全/性能风险 | 用户显式开启、超时、只读检查优先 |
| UI 又变成文件树 | 默认系统卡/任务卡，代码折叠 |
| 现有功能回归 | 每次改动跑全量测试；旧字段只增不改 |
| 范围失控 | 每个里程碑只承诺验收标准内的能力 |
