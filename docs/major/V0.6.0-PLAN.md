## 0. 摘要

v0.6.0 把插件从「**能生成**」推进到「**可确认、可回滚、可恢复、事实可信**」，同时让导入以**注册项**为准。两条主线合并成一个 MINOR：

1. **安全与一致性**（报告 P1 + 第二批）：
   - 路径边界统一（Q01）、事实数据损坏不覆盖（Q05）、解压实际输出上限（Q06）；
   - 任务提交事务（Q03）、项目级串行与 revision/CAS（Q04）、回滚批次（Q07）、幂等生命周期（Q08）；
   - 确认绑定变更内容与基线（Q02）；
   - Client 请求代次与缓存 revision（Q09/Q10）；
   - 预算硬边界、索引可信度、增量扫描（Q11–Q13）；
   - 最小门禁与文档单一事实来源（Q14/Q15）。
2. **注册优先导入**（v0.5.3）：
   - Java 注册解析为权威来源；资源只补全；
   - 扫描 `src/generated/resources`；
   - reimport 清理非注册自动条目 + `import.pruneEntries`。

**核心承诺**：任何一次写操作，要么完整提交、要么完整回滚、要么明确报告「可恢复」；用户确认必须绑定这次变更；提供给 agent 的事实必须可信。

## 1. 背景

### 1.1 自查报告结论

- 无 P0；P1 六项：Q01 路径绕过、Q02 确认门禁、Q03 提交事务、Q04 并发、Q05 损坏覆盖、Q06 解压边界；
- 架构判断：Host 入口轻薄、业务已分模块、HTTP 与工具复用业务函数（值得保留）；缺共享应用命令层、事务边界与 Client 状态契约；
- 建议：先修安全与一致性闭环，再扩功能；不重写、不换数据库、不全库格式化；
- 报告 H 的 9 个待确认问题需先拍板（确认语义、回滚粒度、多进程、HTTP 边界、symlink、运行时版本、静态索引猜测、外部 CI、测试授权）。

### 1.2 v0.5.3 的根因

`corn_crop` 的 blockstate 与模型在 `src/generated/resources`，贴图在 `src/main/resources`；现有扫描只覆盖 main → 父 id 缺失 → `corn_crop_stageN` 成为独立方块；reimport 不删历史条目。

### 1.3 为什么合并

两者都触及同一件事：**事实来源与写入边界**——导入不能凭资源文件猜内容，写入不能绕过确认与保护路径。放在同一 MINOR 可以共用「应用命令层 + 事务 + 校验」基础设施，避免两次改同一条链路。

## 2. 目标与非目标

### 目标

1. 路径策略在**所有入口**使用同一规范路径，`..`/别名/大小写不可绕过；
2. 事实数据损坏时 **fail-closed**（不覆盖、可恢复），派生缓存才允许自动重建；
3. 任务资源与任务记录**统一提交**，失败可区分「已提交/已回滚/恢复失败」；
4. 任务写入有**项目级串行 + revision/CAS**，并发不丢更新；
5. 确认**绑定变更 hash、任务版本与目标文件基线**，`apply` 锁内校验并消费；
6. 回滚语义明确（批次栈或任务级 before-image），幂等记录不假报成功；
7. Client 只提交最新项目/素材请求，缓存按 revision 失效；
8. 导入以注册项为准，`generated` 资源可用，历史残留可清理；
9. 最小门禁（语法 + 测试 + schema 同步）与文档数字校验。

### 非目标

- 不重写、不换数据库、不全库格式化、不迁移 TypeScript；
- 不实现持久事务日志（放到 v0.7 或明确需要时）；
- 不支持多进程一致性的完整方案（先确认是否真实存在，Q04 的 H3）；
- 不改变现有动作名称与数据格式（新增字段向后兼容）。

## 3. 范围（按块）

### 3.1 路径与数据安全（Q01/Q05/Q06）

| 项 | 目标 | 改动 |
| --- | --- | --- |
| Q01 | 所有入口先 `resolve` + 相对化，再做 allowed/guard/备份/写入；拒绝绝对路径与父级跳转 | `lib/paths.js` 新增 `normalizeProjectPath`；`tasks.js` 的 `normalizeApplyFiles`、`checks.js` 的 `matchesPath` 统一使用 |
| Q05 | 区分「文件缺失 / JSON 损坏 / I/O 错误」；损坏时抛明确错误，不返回空数组 | `lib/registry.js` 的 `readJson` 增加 `strict` 模式；`workbench.js`、`registry.js` 事实文件使用 strict |
| Q06 | 解压输出有上限，校验实际长度 | `lib/mdk.js` 的 `inflateRawSync` 加输出上限与累计校验 |

### 3.2 任务提交事务（Q03/Q07）

- 新增 `lib/transaction.js`：`begin()` → `stage()` → `commit()`/`rollback()`，阶段包括备份、资源写入、任务记录、派生刷新；
- `applyTask` 与 `task.codegen.apply` 共用同一提交协议；
- 回滚策略（二选一，见待确认）：批次栈（保留每次 apply 前镜像）或任务级首次 before-image；
- 失败返回 `{ committed, rolledBack, recoveryRequired, backupDir }`，不再吞掉恢复异常。

### 3.3 并发与幂等（Q04/Q08）

- `lib/workbench.js` 增加项目级 Promise 队列（同进程串行）；
- 任务/模块/确认记录增加 `revision`，保存时 CAS（revision 不符返回冲突）；
- 幂等记录绑定 `payload hash + transaction state + generation`；回滚后重放旧 `requestId` 返回 `rolledBack` 而非 `cached`；
- 普通 apply 与 codegen apply 使用同一幂等契约。

### 3.4 确认协议（Q02）

- `task.confirm` 生成**确认凭据**：`{ taskId, revision, payloadHash, fileBaselines, confirmedAt, source }`；
- `apply` 在锁内校验：凭据存在、hash 匹配、文件基线未变；校验后**消费**（一次性）；
- 用户授权来源与 agent 伪造的边界（HTTP 端带用户会话标记；工具端标记为 agent 发起）——需决策（H1）；
- 未确认任务默认拒绝写盘，错误码 `CONFIRMATION_REQUIRED`。

### 3.5 Client 一致性（Q09/Q10）

- `lib/client.js`：项目打开使用请求代次，仅最新请求可提交；项目与素材原子提交；
- 素材 revision：`assets.list` 返回 `revision`（内容 hash 或 mtime 汇总）；图片/预览 effect 依赖 revision 而非数量；
- 切换项目时清空旧操作目标。

### 3.6 注册优先导入（v0.5.3 合并）

- 新增 `lib/registry-scan.js`：解析 `DeferredRegister` + `register("id")` / `registerBlock(...)`，输出 `{ blocks, items, creativeTabs, warnings }`；
- `collectAssets` 合并 `src/generated/resources`（assets 与 data）；
- 条目构建以注册为准，资源只补全；无注册解析时回退资源扫描并标记 `source: 'resource'`；
- reimport 把「自动扫描产生、当前不在注册表」的条目标记/移除（先预览）；
- 新增 `import.pruneEntries { path, dryRun }`。

### 3.7 预算、索引与性能（Q11–Q13）

- `context.pack` 使用 UTF-8 字节预算，最终硬检查；超限返回明确截断说明；
- `api-index` 静态回退限定项目版本、标注可信度、加入 JAR 指纹；
- `structure.refresh` 先算 hash 再决定是否解析，删除检测用集合。

### 3.8 门禁与文档（Q14/Q15）

- `package.json` 增加 `engines`（Node 版本）与 `scripts`：`lint:syntax`（`node --check` 全部入口）、`test`、`gen:schema`；
- 文档数字校验脚本（动作/工具/模板/测试数）纳入测试；
- 文档版本头与计数以单次发版流程更新（已形成，补自动化）。

## 4. 目标架构（渐进）

```text
HTTP adapter / Tool adapter / Client action
        │
        ▼
  应用命令层（lib/commands/*.js）
  校验 → 授权/确认 → revision → 幂等 → 项目锁
        │
        ▼
  领域操作（tasks / workbench / content / import）
        │
        ▼
  基础设施（存储 / 备份 / 进程 / 网络）
        │
        ▼
  可重建缓存（summary / structure / api-index / reference）
```

原则：先抽任务写入链路，不同时迁移全部模块；保留动作名与兼容入口；事实数据与派生缓存错误策略分离。

- 新动作：`import.pruneEntries`（+1）；`task.confirm` 返回确认凭据；`task.apply` 新增 `confirmationId`；

## 8. 风险与兼容

| 风险 | 应对 |
| --- | --- |
| 旧任务/旧备份不兼容新事务 | 读时补默认值；旧 `result` 结构保留；先做兼容测试再改持久格式 |
| 确认协议改变使用流程 | 提供「一键确认（当前 diff）」UI；agent 明确提示需用户确认 |
| 路径严格化拒绝历史合法写法 | 错误信息给出规范路径与拒绝原因 |
| 事务层复杂度过高 | 先覆盖活跃进程；崩溃恢复留给 v0.7 |
| 注册解析漏掉动态注册 | 保留资源扫描回退，输出 warnings |
| Client 改动引入回归 | 先抽状态与纯函数，渲染快照测试保护 |

## 9. 待确认（报告 H + 版本节奏）

1. **确认语义**：批准执行 vs 验收结果——v0.6.0 按「写前批准 + 写后验收」两个状态做？
