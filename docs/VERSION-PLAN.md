# 插件版本规划

> 适用版本：v0.3.2
> 更新日期：2026-11-01
> 本文规定**插件自身**的版本号规则、发版流程与版本历史，与 Minecraft 适配版本无关。
> 版本路线见 [PLAN.md](PLAN.md)，变更明细见 [CHANGELOG.md](CHANGELOG.md)，当前状态见 [STATUS.md](STATUS.md)。

## 0. 为什么需要版本规划

插件已经进入持续迭代阶段：每修复一个 bug、优化一处体验，都会产生一批代码与文档改动。
如果没有统一的版本号，会出现三个问题：

1. **文档对不上代码**：多份文档各自标注不同版本，读者无法判断哪份描述的是当前行为；
2. **改动不可追溯**：一个 bug 修复后，说不清它从哪一版开始生效；
3. **发布靠记忆**：漏跑测试、漏更新 CHANGELOG、漏同步文档。

因此约定：**任何进入仓库的优化或修复，都必须对应一个明确的插件版本号，并同步全部文档。**

## 1. 版本号规则

版本格式为 `vMAJOR.MINOR.PATCH`，按三个阶段理解：

| 阶段 | 版本 | 定位 |
| --- | --- | --- |
| 原型期 | `v0.x.y` | **前期测试原型**：快速迭代，接口、数据与行为都可能调整，不承诺兼容 |
| 稳定版 | `v1.0.0` | **正式稳定版**：从这里开始承诺数据格式与接口契约的稳定 |
| 稳定期 | `v1.x.y` 及以后 | MINOR 对应路线里程碑，PATCH 负责修复与优化，MAJOR 只留给架构变化 |

三段各自的职责：

| 类型 | 含义 | 触发条件 | 示例 |
| --- | --- | --- | --- |
| **MAJOR** | 正式稳定版 / 底层架构 | `v0.x.y` → `v1.0.0` 是发布正式稳定版；`v1.0.0` 之后，只有**底层架构变化**（通常伴随不兼容的数据/接口变更）才 +1 | `v1.4.x` → `v2.0.0`（架构变化） |
| **MINOR** | 路线中的里程碑 | 完成 [PLAN.md](PLAN.md) 里的**一整个阶段目标**，可包含多个功能；完成后 PATCH 归零 | `v0.2.4` → `v0.3.0`；`v1.2.x` → `v1.3.0` |
| **PATCH** | 修复与优化 | bug 修复、行为修正、性能改进、文档校正、兼容性补丁；**里程碑内新增小功能、增强已有功能表现也走 PATCH**，不提前占用下一个 MINOR | `v0.2.1` → `v0.2.2` |

> 三者都是「发布给用户的状态」的编号，不是提交计数。
> 判断顺序：`v0.x.y` 期间按「里程碑 → MINOR，其余 → PATCH」；`v1.0.0` 是稳定版发布；
> `v1.0.0` 之后先看是否发生底层架构变化（是 → MAJOR），再看是否完成里程碑（是 → MINOR），否则 PATCH。
> 三者的改动都必须写 CHANGELOG。

补充约定：

- **`v0.x.y` 是原型期**：不承诺兼容，允许在 MINOR 之间调整接口与数据，但每次不兼容调整都要在 CHANGELOG 标明；
- **口语中的「小版本 +1」指最后一段**：优化 / 修复后把 `v0.2.1` 升到 `v0.2.2`（PATCH），而不是升第二段；
- **一个改动只升一次版本**：同一批相关改动合并为一个版本，不按提交次数累加；
- **PATCH 可以连续发**：修复期间发现新问题，继续 `v0.2.2`、`v0.2.3`，不需要攒成大版本；
- **MINOR 归零 PATCH**：进入 `v0.3.0` 时 PATCH 归零，后续优化从 `v0.3.1` 开始；
- **里程碑内的小功能不升 MINOR**：在当前阶段目标里补一个入口、加一个字段、扩一个交互，都属于 PATCH；
- **架构变化才升 MAJOR**：`v1.0.0` 之后只有底层架构变化（含不兼容的数据/接口变更）才推进 MAJOR；内部重构只要对外行为与数据兼容，就不改变版本号；
- **破坏性更改必须升 MAJOR 并提供迁移说明**（`v1.0.0` 起生效）；0.x 原型期不升 MAJOR，但要在 CHANGELOG 标明「不兼容」；
- **预发布不单独编号**：`Unreleased` 只存在于 CHANGELOG，正式发版时落到具体版本号；
- **插件版本 ≠ 项目 `mcVersion`**：插件版本描述工具本身，`mcVersion` 描述被管理的模组工程，两者互不替代；
- **插件版本 ≠ `schemaVersion`**：数据格式版本由 [DATA-FORMAT.md](DATA-FORMAT.md) 管理，升级时单独迁移。

> 规则调整记录（2026-10-31）：v0.x 定位为前期测试原型，`v1.0.0` 定位为正式稳定版；
> 稳定版之后 MAJOR 只用于底层架构变化，MINOR 对应路线里程碑，PATCH 覆盖里程碑内的修复与新增小功能。
> 此前「MINOR 仅用于新增一组用户可见能力」「MAJOR 用于稳定版」的表述作废，
> v0.2.1 及更早的版本历史仍按当时的规则记录，不追溯改写。

## 2. 版本号的唯一来源

`package.json` 的 `version` 字段是**唯一事实来源**：

```json
{
  "name": "dsh-mcmods-studio-plugin",
  "version": "0.2.1"
}
```

- 代码运行时不硬编码插件版本，避免出现第二份真相；
- 文档中出现的所有「适用版本」必须与 `package.json` 一致；
- 修改版本号时，数据文件字段 `schemaVersion`、项目字段 `minecraft` 均保持原值，不随插件版本联动。

## 3. 每次发版流程

按顺序执行，全部完成才算发版结束：

| # | 步骤 | 产物 / 命令 |
| --- | --- | --- |
| 1 | 判断版本类型（PATCH / MINOR / MAJOR） | 本文第 1 节 |
| 2 | 完成代码改动并补测试 | `test/*.mjs` |
| 3 | 跑语法检查与全量回归 | `for f in index.js client.js lib/*.js; do node --check "$f"; done`；`npm test` |
| 4 | 更新 `package.json` 的 `version` | 例如 `0.2.2` → `0.2.3` |
| 5 | 在 `CHANGELOG.md` 新增版本段 | `Added` / `Changed` / `Fixed` / `Docs` |
| 6 | 更新全部文档的「适用版本」与「更新日期」 | 见第 4 节清单 |
| 7 | 更新本文第 5 节版本历史 | 记录版本、日期、类型、要点 |
| 8 | 核对文档中的数量与事实 | 工具数、动作数、测试数、文件数、目录结构 |
| 9 | 提交 | 建议提交信息：`release: vX.Y.Z` 或 `feat/fix: ... (vX.Y.Z)` |
| 10 | Host 代码有改动时重装 bundle 验证 | `remove_bundle` → `install_bundle` → 刷新页面 |

> 第 9 步不是可选项：**发版必须对应一个提交**，否则版本号与代码状态无法互相印证。

## 4. 文档同步清单

「为所有文档更新」不是一句口号，按下表逐项检查：

| 文档 | 何时必须改 | 改什么 |
| --- | --- | --- |
| `package.json` | 每次发版 | `version` |
| `CHANGELOG.md` | 每次发版 | 新增版本段，写清新增 / 变更 / 修复 / 文档 |
| `VERSION-PLAN.md` | 每次发版 | 头部版本、更新日期、第 5 节历史 |
| `docs/PLAN.md` | 发版时 | 当前版本、路线状态、技术分层（新增模块时） |
| `docs/STATUS.md` | 发版时 | 适用版本、需求对照、已实现 / 未实现、验证状态 |
| `docs/INDEX.md` | 代码结构或接口变化时 | 文件地图、函数表、动作表、工具表、测试索引、行数 |
| `docs/ARCHITECTURE.md` | 分层或数据流变化时 | 模块图、生命周期、边界 |
| `docs/DATA-FORMAT.md` | 数据文件或字段变化时 | 目录、字段表、派生文件说明 |
| `docs/DEVELOPMENT.md` | 目录、命令、约定变化时 | 代码结构、数据流、扩展方式、测试方式 |
| `docs/COMPATIBILITY.md` | 支持范围或加载器差异变化时 | 版本矩阵、差异表、非目标 |
| `docs/PROJECT-STRUCTURE.md` | MC 工程结构或写入落点变化时 | 路径、落点表、官方依据 |
| `docs/BUILD-GUIDE.md` | 构建流程或版本要求变化时 | JDK、加载器、命令行、常见问题 |
| `docs/plans/*.md` | 模块职责、接口、缺口变化时 | 「适用版本」、状态、接口表、现状与缺口 |
| `docs/plans/README.md` | 模块增删或状态变化时 | 模块一览、状态列、依赖图 |
| `docs/refactor/*.md` | 仅修死链或补历史标注 | **不回落历史数字**：文中计数是当时结果，保留原样 |
| `README.md` | 功能、安装、文档入口变化时 | 功能列表、版本策略、文档链接 |

**统一头部格式**（新增或修订文档时使用）：

```text
> 适用版本：vX.Y.Z
> 更新日期：YYYY-MM-DD
```

## 7. 与 CHANGELOG 的分工

| 文档 | 回答的问题 | 读者 |
| --- | --- | --- |
| `VERSION-PLAN.md`（本文） | 版本号怎么定、发版要做什么、版本之间是什么关系 | 维护者 |
| `CHANGELOG.md` | 每个版本具体改了什么 | 用户与维护者 |
| `STATUS.md` | 现在能做什么、还不能做什么 | 用户与 agent |

三者不重复维护同一份事实：版本号规则只在本文，变更明细只在 CHANGELOG，能力现状只在 STATUS。

## 8. 常见问题

**Q：只改文档也要升版本吗？**
A：如果文档校正伴随代码行为变化，随该次发版走；如果只是修正错别字、死链、补充说明，不改变行为，可并入下一个 PATCH，不单独发版。

**Q：一次修复涉及多个模块，要升几次？**
A：一次。版本描述的是「发布给用户的状态」，不是提交数量。

**Q：紧急修复能不能跳过测试？**
A：不能。至少跑 `npm test`，并在 CHANGELOG 注明修复范围；如果测试本身缺失，先补测试再发版。

**Q：`v0.x` 算正式版吗？**
A：不算。`v0.x` 是前期测试原型：可以给早期用户使用，但接口、数据与行为都可能调整，不承诺兼容；不兼容调整要在 CHANGELOG 标明。

**Q：什么时候进入 `v1.0.0`？**
A：路线里程碑（M5）完成、数据格式与接口契约稳定、全量回归通过时发布 `v1.0.0`，它是**正式稳定版**，不是架构变更。

**Q：什么时候升 MINOR？**
A：完成 [PLAN.md](PLAN.md) 里的一个里程碑、并达到它的验收标准时。一个 MINOR 可以包含多个功能；不要求在版本号节奏上「一功能一 MINOR」。

**Q：在里程碑里加一个小功能，要升 MINOR 吗？**
A：不要。当前阶段目标内新增小功能、扩展现有交互、优化表现，都按 PATCH 递增。

**Q：`v1.0.0` 之后什么时候升 MAJOR？**
A：发生底层架构变化时，通常伴随不兼容的数据或接口变更（旧工程/旧备份需要迁移）。升 MAJOR 必须同时提供迁移说明。

**Q：内部重构要升 MAJOR 吗？**
A：不要。只要对外行为、数据格式与已有工程保持兼容，重构不改变版本号，随当次 PATCH 或 MINOR 记录即可。
